Ο καθολικός μετασχηματισμός

Επαναλαμβάνεται σχεδόν αυτούσιος σε 20 queries. Στη νέα υλοποίηση γίνεται μία φορά, σε επίπεδο view ή ETL job:

-- SQL Server ισοδύναμο του Power Query βήματος
SELECT
    PARSENAME(REPLACE(CollectionName,'_','.'),4) AS GreaterArea,
    PARSENAME(REPLACE(CollectionName,'_','.'),3) AS CollectionName,
    PARSENAME(REPLACE(CollectionName,'_','.'),2) AS Category,
    COALESCE(PARSENAME(REPLACE(CollectionName,'_','.'),1),'2019H2') AS Scope,
    CollectionName AS STR_ID,          -- ταυτόσημο με το concat των 4
    *
FROM BI_DATA.dbo.BI_Capacity;
Προσοχή: το PARSENAME κόβεται στα 4 μέρη — αν κάποιο CollectionName έχει παραπάνω από τρεις κάτω παύλες, χρειάζεσαι STRING_SPLIT με ordinal ή CLR split. Το Power Query σιωπηλά κρατάει τα 4 πρώτα.

Ο πίνακας-κλειδί

ALL INFO SYNCED FILTERS δεν έρχεται από δικό του πίνακα — παράγεται από το BI_Capacity:

SELECT DISTINCT CollectionName, MIN(CallDate) AS StartDate
FROM BI_Capacity
GROUP BY CollectionName;
Συνέπεια: αν ένα collection υπάρχει στο voice αλλά όχι στο capacity, δεν εμφανίζεται σε κανέναν slicer. Στη νέα βάση φτιάξε τη διάσταση ως UNION όλων των fact tables, όχι μόνο του Capacity.

Το μοτίβο «(groups)»

Σε κάθε πίνακα γεγονότων υπάρχει calculated column HomeOperator (groups) με ταυτόσημο περιεχόμενο. Είναι η ενοποίηση Wind + NOVA:

SWITCH(TRUE,
  ISBLANK([HomeOperator]),          "(Blank)",
  [HomeOperator] IN {"Cosmote"},    "Cosmote",
  [HomeOperator] IN {"NOVA","Wind"},"Nova",
  [HomeOperator] IN {"Vodafone"},   "Vodafone",
  [HomeOperator])

Στη νέα βάση αυτό γίνεται ένας πίνακας διάστασης dim_operator(raw_name, display_name) και ένα join — όχι 14 αντίγραφα του ίδιου CASE.

Η αλυσίδα

  1. Διαχωρισμός Voice / Datavoice_total_weight = Voice_scores_total · Data weight = 100 − voice_total_weight
  2. Correction factorsΚανονικοποιούν ώστε τα βάρη να αθροίζουν στο επιθυμητό ποσοστό:
    CF_DATA = 10 × Data weight ÷ (HTTP×100 + Cap×275 + Brw×100 + YT×100 + Ping×25)
    CF_VOICE = 10 × voice_total_weight ÷ (GSM×150 + FREE×250)
  3. Τελικά βάρηping weight = 25 × Ping_val × CF_DATA · HTTP Weight = 100 × … · Capacity Weight = 275 × … · Browsing weight = 100 × … · youtube weight = 100 × … · voice GSM weight = 150 × GSM_val × CF_VOICE · voice_scores Free weight = 250 × FREE_val × CF_VOICE
  4. Grades ανά υπηρεσίαGrade X = Σ (SUB_SCORE_X × weight_X) πάνω στα φιλτραρισμένα rows
  5. Aggr points ανά rowGrade HTTP + Grade Capacity + Grade Browsing + Grade ping + Grade Youtube + Grade FREE + Grade GSM
  6. Τελικό σκορVisuals Total Score = Σ(WEIGHT × aggr_points) ÷ Σ(WEIGHT) — σταθμισμένος μέσος ανά κατηγορία περιοχής
  7. Διαφορές22 measures της μορφής [X]@Cosmote − [X]@Vodafone και [X]@Cosmote − [X]@(Wind ∪ NOVA)

Όλο μαζί σε SQL

WITH params AS (            -- έρχονται από το UI, όχι από πίνακα
  SELECT 60::numeric AS voice_total, 40 AS gsm, 60 AS free,
         50 AS cap, 50 AS http, 50 AS brw, 50 AS yt, 50 AS ping
),
cf AS (
  SELECT *,
    (100 - voice_total)                                   AS data_weight,
    10.0 * (100 - voice_total)
      / NULLIF(http*100 + cap*275 + brw*100 + yt*100 + ping*25, 0) AS cf_data,
    10.0 * voice_total
      / NULLIF(gsm*150 + free*250, 0)                     AS cf_voice
  FROM params
),
w AS (
  SELECT
    ping*25  * cf_data  AS w_ping,   http*100 * cf_data AS w_http,
    cap*275  * cf_data  AS w_cap,    brw*100  * cf_data AS w_brw,
    yt*100   * cf_data  AS w_yt,
    gsm*150  * cf_voice AS w_gsm,    free*250 * cf_voice AS w_free
  FROM cf
),
rows AS (
  SELECT s.operator, s.weight,
         s.sub_score_http*w.w_http + s.sub_score_cap*w.w_cap
       + s.sub_score_browsing*w.w_brw + s.sub_score_ping*w.w_ping
       + s.sub_score_yt*w.w_yt + s.sub_score_free*w.w_free
       + s.sub_score_gsm*w.w_gsm                          AS aggr_points
  FROM bi_scores_total s CROSS JOIN w
  WHERE s.str_id = ANY(:selected_str_ids)
)
SELECT operator,
       SUM(weight * aggr_points) / NULLIF(SUM(weight),0)  AS total_score
FROM rows GROUP BY operator;
Καλά νέα για τη μεταφορά: η αλυσίδα είναι καθαρά αριθμητική και τα SUB_SCORE_* είναι ήδη υπολογισμένα στη βάση. Μπορείς να στείλεις μόνο τα rows στο frontend και να ξαναϋπολογίζεις το σκορ τοπικά καθώς ο χρήστης σέρνει τα sliders — χωρίς round-trip.
Ένα σφάλμα προς διόρθωση: το Voice weight GSM = 100 − Voice_scores FREE Value δηλώνει ότι GSM και FREE είναι συμπληρωματικά, αλλά κανένα measure δεν το χρησιμοποιεί — τα δύο sliders είναι ανεξάρτητα. Αν θέλεις τη συμπληρωματικότητα, επίβαλέ την στο UI.

07 · Full-stack πλάνο

Πώς το ξαναχτίζεις καλύτερα

Η λογική μεταφέρεται από το DAX στη βάση. Το frontend γίνεται λεπτό: ένα filter store, ένα query layer, μια βιβλιοθήκη charts.

Επίπεδα

  1. Αποθήκευση — SQL Server ή PostgresΚράτα τους πίνακες BI_* ως έχουν. Πρόσθεσε: dim_collection (η αντικατάσταση του ALL INFO SYNCED FILTERS, ως UNION όλων των fact tables), dim_operator, dim_category_weight, και τα 4 Excel ως κανονικούς πίνακες. Ένα collection_id INT surrogate key αντί για το string STR_ID κάνει τα joins πολλαπλάσια πιο γρήγορα.
  2. Προϋπολογισμένα aggregatesΚάθε σελίδα ζητά ουσιαστικά «KPI × operator × collection × scope». Φτιάξε ένα materialized view ανά άξονα (mv_voice_kpi, mv_data_kpi, mv_scanner_kpi) με τα counters και τα percentiles ήδη υπολογισμένα ανά collection_id × operator. Το 90% των 837 visuals σερβίρεται από αυτά χωρίς να αγγίξεις τα raw rows.
  3. API — FastAPIΛίγα, γενικά endpoints αντί για ένα ανά chart:
    GET /api/dimensions → τιμές για τα slicers
    POST /api/kpi → {axis, metrics[], groupBy[], filters{}} → rows
    POST /api/scores → τα SUB_SCORE_* + WEIGHT· η στάθμιση γίνεται client-side
    POST /api/geo → GeoJSON ή Arrow για τους χάρτες
    GET /api/drill → raw rows για τα δύο drill-through tables
  4. Μεταφορά μεγάλου όγκουΟι χάρτες στέλνουν δεκάδες χιλιάδες σημεία. Χρησιμοποίησε Apache Arrow ή Parquet αντί για JSON — pyarrow στο FastAPI, apache-arrow στο React. Για τα binned scanner data (50 m/500 m) στείλε ήδη aggregated bins, ποτέ raw samples.
  5. Κατάσταση φίλτρων — το κρίσιμοΈνα zustand (ή Redux) store με το σχήμα των slicers: {greaterArea[], collection[], category[], scope[], dateRange, device, operators[]}. Κάθε chart είναι selector πάνω σε αυτό. Αυτό αντικαθιστά ολόκληρο τον μηχανισμό sync slicers του Power BI.
  6. Charts — EChartsΚαλύπτει line, bar, stacked, pie, donut, treemap, funnel, gauge, scatter — δηλαδή όλα εκτός των χαρτών, με ένα configuration API. Εναλλακτικά visx αν θέλεις πλήρη έλεγχο.
  7. Χάρτες — MapLibre GL + deck.glScatterplotLayer για τα drive-test points (χρωματισμός από το throughput bin), GridCellLayer/H3HexagonLayer για τα 50 m & 500 m scanner bins, IconLayer για το best-operator map. Δωρεάν αντικαταστάτης του Azure Maps, με καλύτερη απόδοση σε >100k σημεία.
  8. Πίνακες — AG Grid ή TanStack TableΓια τα 12 pivotTables και τα 2 drill-through tables. Το AG Grid Enterprise κάνει pivot native· το TanStack θέλει να στείλεις ήδη pivoted rows από το API.
