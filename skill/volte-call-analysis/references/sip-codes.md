# SIP codes: network or user (md §1.5)

The user-code list is configuration (`src/lib/mdClassifier/config.ts`), not hard-coded: each benchmarking methodology defines it differently.

| Code | Meaning | Category |
|---|---|---|
| 180 / 200 | Ringing / OK | success (first of the two counts) |
| 486 | Busy Here | user — invalid test in benchmarking |
| 603, 604 | Decline / does not exist | user (TL 9000 VSSR counts them as success) |
| 487 | Request Terminated after CANCEL | user if the user cancelled, **network fail** if the network cancelled |
| 404 | Not found | test misconfiguration → invalid |
| 408, 480 | Timeout / temporarily unavailable | network fail (check 480 case by case) |
| 500, 503, 504 | Server errors | network fail |
| 580 | Precondition failure | network fail (stage PRECONDITION) |

## ACK semantics (RFC 3261)

- For a **non-2xx** final response to INVITE, the ACK is part of the INVITE transaction and is generated by the client transaction (§17.1.1.3).
- For a **2xx**, the ACK is a separate transaction generated by the UAC core (§13.2.2.4).
- Consequence: `IMS SIP ACK: Request` after `INVITE: Request Terminated` (487) belongs to a call that was cancelled, not connected. Check which response the ACK follows before using it as "call connected".

## Where the codes appear in the data

- Tracelog: `IMS SIP INVITE Error NNN` (A and B side).
- `call_analysis`: `SIPINVITECode` / `SIPBYECode` as text (e.g. "Session Progress", "Server Internal Error", "Request Terminated").
- `l3_messages` layer `SIP`: `CombinedMsgNameSIPResponse`, e.g. `IMS SIP INVITE: Request Terminated`, `IMS SIP ACK: Request`.
